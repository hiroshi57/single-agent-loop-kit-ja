# 記事要約: 「サブエージェントをメインループに畳み込むべきとき」

> 原文: Anthropic公式 "Building agents: When to fold subagents into your main agent loop"
> (2026-10-22)。本ドキュメントは要点を日本語で再構成した独自ダイジェストであり、
> 公式記事の翻訳ではありません。一次情報は必ず原文を確認してください。

## 結論

- マルチエージェント(ルーター/オーケストレーター + 専門サブエージェント群)は、
  今のモデル(Opus 4.5以降)の能力を踏まえると**過剰設計になりやすい**。
- 「1モデル・1コンテキスト・スキル/ツールをオンデマンドで読み込む単一ループ」に
  畳み込むと、巨大プロンプト構成にもサブエージェント並列構成にも**品質で勝つ**ことが
  多く、速度・コストも改善しやすい。
- ただし「全部畳め」ではない。**測定してから判断する**のが大前提。

## 数字(公式記事が挙げているもの)

| 指標 | 内容 |
|---|---|
| 実行速度 | マルチエージェント→単一ループで約2倍速くなった事例あり |
| システムプロンプト | Claude Code自身のプロンプトを新モデル向けに80%以上削減 |
| ツール数 | システムプロンプト内のツール定義が30〜50個を超えると選択精度が落ち始める |
| 最小構成の目安 | 明確なシステムプロンプト1本 + 薄いデータ取得ツール4〜5個 + 出力ガードレール |

## なぜ部下(サブエージェント)を増やすと劣化するか

1. **lossy handoffs(欠落する引き継ぎ)**: 担当間で要約を渡すたびに文脈(緊急度・
   背景・言外の制約)がこぼれ落ちる。各部下は「上司が要約した切り抜き」しか見えない。
2. **コンウェイの法則**: 組織(チーム別)に合わせてサブエージェントを割り当てると、
   エージェント構成がそのまま組織図のコピーになり、以下5つの失敗が起きやすい。
   - 話の受け渡し問題(lossy handoff の具体化)
   - 部下の大量発生(責任者不明のサブエージェントが増殖)
   - フランケンプロンプト(チームごとに指示を継ぎ足して矛盾だらけになる)
   - 部分最適な採点表(各チームが自分の担当だけを見た評価を積み上げる)
   - レイテンシ悪化(構成が複雑になるほど遅くなる)

## 単一ループでの情報の置き場所

| 置き場所 | 役割 | 例 |
|---|---|---|
| **スキル(Skill)** | 手順・判断基準(「どう進めるか」) | 返品対応の進め方、言葉づかいルール |
| **ツール(Tool)** | 実行・最新データ取得・構造化された結果 | API呼び出し、DB更新。**API単位ではなく「ユーザーがやりたいこと」単位でまとめる** |
| **知識ベース** | 規約・定義・仕様などの参照資料 | モデルが検索ツールで必要な分だけ取りに行く。プログラム側で丸ごと貼り付けない |

- ツール側に前提条件チェックを埋め込む(例: 「Yをやるにはまず先にXが要る」を
  ツールがチェックし、不足時はClaudeが読める指示を返す)
- 権限チェックもツール側に埋め込む(「この人はこれを見ていいか」を都度ツールが判定)
  → 権限レベルごとに別エージェントを作らなくて済む

## 単一ループの運用ルール(概要)

- 1モデル・1作業スペース
- ターン数上限・トークン上限・書き込み前の承認ゲートは仕組み側で固定
- 毎ターン、ツール呼び出しをバッチでまとめて並列実行し、生の結果をそのままモデルに返す
- **計画を立てる人と実行する人が同じ**: 結果が届くたびに計画を書き直せる
  (サブエージェント構成だと計画係と実行係が分離し、ズレの修正に往復が要る)

## それでもサブエージェントが要る3つの場面

1. 1ループだとコンテキストが膨らみすぎて、**数字で測って**性能が落ちているとき
2. 独立した調べ物を**並行**で走らせ、終わったら捨ててよいとき
3. ツール選びが迷子になる、またはシステムプロンプト内の指示同士が矛盾しているとき

→ 分割の基準は「問題の種類」ではなく「必要な情報のまとまり」。
　他から情報をほとんど貰わずに完結し、コンパクトな結果だけ返せる仕事を渡す。

## 移行手順(4ステップ)

1. **採点表(eval)を先に作る**: 正解例10件程度でよい。全体用の採点表は中央チームが
   1つ、スキル単位の小さい採点表はそのスキルを作ったチームが持つ。
2. **よく一緒に動く部下からまとめる**(マージ): 片方の出力をもう片方が使っている、
   同じデータを触っている、いつもセットで呼ばれている、といった関係が深いペアから。
3. **部下を「ツールとして呼ぶ」形に一度変える**: いきなり消さず中間状態を経由する。
   ここで一度採点し、「畳む前の実力」を数値として残す。
4. **1人ずつスキル/ツールに置き換えて都度比較**: 最終スコアだけでなく、
   **どのタスクの結果がひっくり返ったか**を1件ずつ確認する。

## 失敗事例(公式記事内)

ある部下を畳み込んだ際、待ち時間は改善したが「配送日の確認」をメインエージェントが
勝手に省略するようになり、1つの処理だけが静かに壊れていた。しかも2回中1回でしか
再現しなかった。→ **本番でセットになって動く流れ全てにテストを用意し、各テストは
複数回走らせること。**
